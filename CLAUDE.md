# AI Customer Support Platform — Project Context

This file gives Claude Code persistent context on this project. Read it fully before making changes. Update the "Current Progress" section at the end of each work session so future sessions pick up where you left off.

## Elevator Pitch

An enterprise-style AI-powered customer support platform combining a Laravel backend for business logic and ticketing, a FastAPI microservice for AI/RAG operations, a React frontend for both the customer chat widget and the admin dashboard, backed by a shared PostgreSQL database (with pgvector) and a pluggable LLM layer (OpenAI, Anthropic, or Groq). Built as a portfolio piece to demonstrate polyglot microservice architecture, applied AI (RAG, sentiment, summarization), clean API design, and enterprise development practices (auth, async queues, testing, deployment).

## Tech Stack

- **Backend (business logic):** Laravel 12, PHP 8.2+, Sanctum for auth, Redis-backed queues
- **AI microservice:** FastAPI, Python 3.11+, SQLAlchemy + Alembic (migrations), pgvector, psycopg2, sentence-transformers
- **Frontend:** React 19 + Vite 8 + TypeScript, axios, react-router-dom
- **Database:** PostgreSQL 15+ with the `pgvector` extension enabled
- **Queue/cache:** Redis
- **AI provider:** chat is pluggable via a strategy pattern in `app/services/llm/` (`base.py` + one module per provider + `factory.py`), selected at runtime by the `LLM_PROVIDER` env var — currently supports `openai`, `anthropic`, and `groq` (Groq's free tier is the default for local dev, since OpenAI/Anthropic both require paid credits). Embeddings use a local `sentence-transformers` model (`all-MiniLM-L6-v2`, 384-dim) via `app/services/embeddings.py` — no per-request API cost, same model for ingestion and query-time retrieval.

## Architecture Rules (non-negotiable)

1. **React talks only to Laravel.** The frontend never calls FastAPI directly. This keeps one clean public API surface.
2. **Laravel talks only to FastAPI for AI work.** Laravel owns tickets, users, auth, and orchestration; it forwards AI-specific requests (chat, ingest, sentiment, summarize) to FastAPI over HTTP.
3. **Service-to-service auth:** Laravel → FastAPI calls are authenticated with a shared secret header (e.g. `X-Internal-Api-Key`), verified in FastAPI's `core/security.py`. This is not user-facing auth — it just proves the request came from Laravel.
4. **One Postgres instance, two owners.** Laravel's Eloquent migrations own the business tables (`users`, `agents`, `tickets`, `messages`). FastAPI's SQLAlchemy models own the vector table (`document_chunks`). Neither service should write migrations for the other's tables.
5. **Anything slow or non-interactive goes through a Laravel queue job** (email polling, summarization, sentiment scoring, document ingestion) — never block an HTTP request on an LLM call longer than a simple chat turn.

## Data Flows

**Chat / RAG flow:** customer sends a message in the widget (identified by a client-generated `visitor_id` from `localStorage`, no auth — the widget is anonymous) → Laravel finds the visitor's open ticket or creates one, logs the message, calls FastAPI `/chat` with the message → FastAPI embeds the query, runs a pgvector similarity search over `document_chunks`, computes the minimum cosine distance across retrieved chunks, builds a RAG prompt, calls the configured LLM provider (`app/services/llm/factory.py`) → returns `{reply, escalate}`, where `escalate` is `true` when no chunks were retrieved or the minimum distance exceeds `CONFIDENCE_DISTANCE_THRESHOLD`. Laravel stores the bot reply as a message, marks the ticket `escalated` if flagged (a failed/unreachable FastAPI call also forces `escalate: true` as a fail-safe), and returns `{reply, ticket_id, escalated}` to React, which shows a human-handoff notice when escalated.

**Document ingestion flow:** an agent uploads a document → Laravel stores the file and queues `IngestDocumentJob` → the job calls FastAPI `/ingest` (throws on failure, so it lands in `failed_jobs` instead of silently succeeding) → FastAPI chunks the text, generates embeddings via `sentence-transformers` (`all-MiniLM-L6-v2`), and writes rows into `document_chunks`.

**Email summarization flow:** a scheduled Laravel command (`email:poll`, `Schedule::command('email:poll')->everyFiveMinutes()` in `routes/console.php`) connects to the support inbox via IMAP (`webklex/laravel-imap`, config in `config/imap.php`), fetches unseen messages in the configured folder, and for each one (wrapped in its own try/catch so one malformed email doesn't abort the batch) creates a **new** `Ticket` (`visitor_id` = sender email — no threading by subject/In-Reply-To, that's a documented future enhancement) and a customer `Message` (body prefixed with `"Subject: {subject}\n\n"`), dispatches `SummarizeEmailJob` and `AnalyzeSentimentJob`, then marks the email seen — only after the ticket/message are successfully created, so a failure leaves it unread for retry on the next poll rather than losing it. `SummarizeEmailJob` calls `AiServiceClient::summarize()` → FastAPI `/summarize` and saves the result on `tickets.summary`. FastAPI's side (`app/api/summarize.py`) is built: short inputs (under ~40 words) are returned unchanged to skip a wasted LLM call; otherwise it calls `get_llm_provider()` (same abstraction as `/chat`/`/sentiment`) with a system prompt asking for a plain-text 2-3 sentence summary (key issue + requested action, no markdown/preamble). Unlike `/sentiment`, it doesn't catch provider exceptions — there's no JSON to fail-parse, and this matches `/chat`'s existing convention of letting `AiServiceClient` handle failures on the Laravel side. Surfaced in the dashboard as an "AI Summary" callout above the message thread in `TicketDetailPage`, shown only when `ticket.summary` is present.

**Sentiment flow:** FastAPI `/sentiment` (`app/api/sentiment.py`) takes `{text}`, sends it to the configured LLM provider (`get_llm_provider()`, same strategy as `/chat` — no separate ML model/library) with a system prompt instructing strict-JSON-only output, parses the response (stripping markdown code fences some providers add despite instructions) into `{label, score}`, and falls back to `{"neutral", 0.5}` on any parse failure or provider error rather than raising — sentiment is a nice-to-have signal, not something that should break the ticket flow. The Laravel side (an async job triggered per inbound customer message, storing the result on the message, rolling it up onto the ticket, and surfacing it on the dashboard queue) is not built yet — see Week 4 below.

**Sentiment scoring (Laravel side):** immediately after `ChatController` creates the customer's `Message` (never the bot's), it dispatches `AnalyzeSentimentJob::dispatch($message)` → the job calls `AiServiceClient::sentiment()` (POST `/sentiment`, same auth/timeout/fallback pattern as `chat()`/`ingest()` — connection failure or non-2xx response returns `{'label' => 'neutral', 'score' => 0.5}` rather than throwing, so a flaky AI service never blocks message creation) → saves `sentiment_label`/`sentiment_score` on the message, then recomputes the ticket's `sentiment_summary` as the worst label across all its customer messages so far (negative > neutral > positive) and saves it if changed. Surfaced in the dashboard as colored badges (`badge-sentiment-<label>`) in both `TicketListPage`'s Sentiment column and `TicketDetailPage`'s header + per-message tags; the sentiment filter dropdown (already built in Week 3) now actually narrows results now that tickets have real `sentiment_summary` values.

**Agent flow:** agent logs in via the React `LoginPage` (`src/dashboard/`), which calls `POST /login` (email/password checked against the `agents` table, returns a Sanctum `plainTextToken` + agent info) → `AuthContext` stores the token/agent in `localStorage` and an axios request interceptor (`src/api/client.ts`) attaches `Authorization: Bearer <token>` to every subsequent request → `ProtectedRoute` (`src/auth/`) guards `/dashboard` and `/dashboard/tickets/:id`, redirecting to `/login` when unauthenticated → both routes render nested inside `DashboardLayout` (single header with logo/agent name+role/logout, via `<Outlet/>`) → `TicketListPage` lists tickets (`GET /tickets`, plain array response) with a logout button (`POST /logout` revokes the token) → clicking a ticket opens `TicketDetailPage` (`GET /tickets/{id}`, messages eager-loaded in chronological order), which lets the agent reply (`POST /tickets/{id}/messages`, `sender: 'agent'`, flips `escalated` → `in_progress`) or mark it resolved (`PUT /tickets/{id}` with `{status: 'resolved'}`, which also hides the reply form and resolve button client-side). Replying to an unassigned ticket auto-assigns it to the replying agent. Non-admin agents only see tickets that are unassigned or assigned to them (`TicketController@index`); admins see all. `EnsureIsAdmin` middleware (aliased `admin` in `bootstrap/app.php`) additionally gates `POST /documents` to admins only. `TicketListPage` has status/priority/sentiment filter dropdowns (`?status=&priority=&sentiment=` on `GET /tickets`).

## Database Schema (high level)

- `users` — customer/end-user accounts
- `agents` — support agents/admins, role field (agent/admin)
- `tickets` — id, user_id (nullable), visitor_id (nullable, indexed — anonymous widget visitors or, for email-originated tickets, the sender's email address), status, priority, sentiment_summary, assigned_agent_id, summary (nullable, AI-generated gist for email-originated tickets), timestamps
- `messages` — id, ticket_id, sender (customer/bot/agent), body, sentiment_label, sentiment_score, timestamps
- `documents` — id, title, source_file, content (nullable, full text — durable copy, since the local disk `source_file` points at isn't durable on a free-tier host), uploaded_by, timestamps
- `document_chunks` — id, document_id, chunk_text, embedding (vector), timestamps

## Environment & Service Communication

- Laravel `.env`: standard Postgres connection vars, Redis connection vars, `AI_SERVICE_URL` (FastAPI base URL), `AI_SERVICE_SECRET` (shared secret sent to FastAPI), `FRONTEND_URL` (the one allowed CORS origin, `config/cors.php` — default `http://localhost:5173`), `IMAP_HOST`/`IMAP_PORT`/`IMAP_ENCRYPTION`/`IMAP_USERNAME`/`IMAP_PASSWORD`/`IMAP_FOLDER` (support inbox polled by `email:poll`, wired into `config/imap.php`)
- FastAPI `.env`: `LLM_PROVIDER` (`openai` | `anthropic` | `groq`), the matching `<PROVIDER>_API_KEY` / `<PROVIDER>_MODEL` pair (all three pairs may be present; only the selected provider's is required), `INTERNAL_API_KEY` (must match Laravel's `AI_SERVICE_SECRET`), `DATABASE_URL` (same Postgres instance), `CONFIDENCE_DISTANCE_THRESHOLD` (min pgvector cosine distance across retrieved chunks above which `/chat` sets `escalate: true`; calibrated to `0.65` for the `all-MiniLM-L6-v2` model — `0.4` was too strict and escalated most real paraphrased questions, not just poorly-covered ones)
- React `.env`: `VITE_API_BASE_URL` pointing at Laravel only
- Default local ports: Laravel `8000`, FastAPI `8001`, React `5173`, Postgres `5432`, Redis `6379`

## Development Commands

**Laravel:** `php artisan serve` to run, `php artisan test` for PHPUnit, `php artisan migrate` for schema changes, `php artisan queue:work` to process jobs locally.

**FastAPI:** `uvicorn app.main:app --reload --port 8001` to run, `pytest` for tests.

**React:** `npm run dev` to run, `npm run build` for production build.

**Postgres:** enable the extension once per database with `CREATE EXTENSION IF NOT EXISTS vector;`

## Coding Conventions

- Laravel: PSR-12, use Form Requests for validation, keep controllers thin (business logic in Services)
- FastAPI: full type hints, Pydantic schemas for all request/response bodies, one router per resource under `app/api/`; LLM calls always go through the `LLMProvider` strategy in `app/services/llm/` — never call a provider SDK directly from a route. Add a new provider by implementing `LLMProvider` and registering it in `factory.py`.
- React: TypeScript strict mode, functional components with hooks, keep `widget/` and `dashboard/` visually and logically separate even though they share the `api/` client layer and the single shared `styles/global.css` (navy/blue design system: CSS variables, `.btn-primary`/`.btn-secondary`, `.badge`/`badge-<status>`, `.message`/`message-<sender>`, `.empty-state`); dashboard pages share layout via `DashboardLayout` (header/logout, nested under `ProtectedRoute` in `App.tsx`) rather than each page rendering its own header
